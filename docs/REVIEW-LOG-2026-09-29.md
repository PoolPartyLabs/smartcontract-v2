# Review log, 2026-09-29: module builds, adversarial verification findings and open questions

Each module was written by one agent in its own branch, then adversarially verified (unit, fuzz, invariant and mainnet-fork tests, Slither, decision-by-decision review) with up to two fix rounds. Blocking findings were fixed before merge; the lists below are the final non-blocking findings and the open questions the builders raised. Items marked as handled in the consolidation pass are referenced from the commits that close them.


## across-bridge-adapter

### Interface changes requested by builders

- IAcrossSpokePool (frozen): the depositV3 parameter named `exclusivityDeadline` is Across's `exclusivityParameter` (0 / offset <= 31,536,000 / absolute timestamp) and requires a non-zero exclusiveRelayer when non-zero. The NatSpec, and IBridgeAdapter.SendRequest.exclusivityDeadline, should say so. It could also list `pausedDeposits()` and state that `enabledDepositRoutes` no longer exists. The NatSpec also omits that quoteTimestamp must not be in the future. Documentation only; no ABI change.
- IBridgeAdapter.InvalidParty is documented as 'Recipient or depositor is zero'. The adapter also uses it for a bytes32 recipient with bits above 160 (not an EVM address), to honour 'never substitutes a recipient'; the NatSpec could be widened to cover that.

### Open questions raised by builders

- **QA6 (DEC-066)**: Per-send keyless TransitEscrow as the Across depositor is still the research proposal, pending the founder's confirmation. Code: buildSend requires a non-zero depositor and encodes it as the depositV3 depositor; NatSpec states it must be a keyless TransitEscrow clone. The fork tests prove FundsDeposited.depositor equals the clone.
- **QA19**: Max bridge fee per send (maxBridgeFeeBps value). Code: Not checked in the adapter; the vault enforces it before buildSend. The adapter only enforces outputAmount <= inputAmount (sound for USDC/USDG, both 6 decimals).
- **Q17-4**: Whether the adapter codehash is pinned or revalidated. Code: The adapter has immutable code (no proxy, no selfdestruct). The test harness pins target and codehash at creation and revalidates the codehash on every send, as the vaults are expected to.
- **FACT-across-route-list**: The live SpokePools on Arbitrum (impl 0xcfcda84333431bcc9155f2368b8362f0d1dff8c9) and Robinhood (impl 0x1771c470d41b8c39338450c380bf2c080a2cedd8) no longer have enabledDepositRoutes, so no on-chain route flag exists. Whether relayers fill USDC(42161)->USDG(4663) and USDG(4663)->USDC(42161) is off-chain; an unfilled deposit expires and refunds to the escrow. Code: The fork tests assert pausedDeposits == false, buffers 21600/3600, that the enabledDepositRoutes call reverts with empty data, and that a real depositV3 succeeds with the exact event. Nothing is faked.
- **FACT-exclusivity-parameter**: The SpokeVault/CoreVault authors must know that SendRequest.exclusivityDeadline is Across's exclusivityParameter: 0 means none, a value up to 31,536,000 is an offset from deposit time, a larger value is an absolute timestamp, and a non-zero value requires a non-zero exclusiveRelayer (otherwise InvalidExclusiveRelayer). Code: The adapter encodes the value as received without validating it; the pool enforces the rule and the vault transaction reverts atomically. A fork test covers both the absolute and the offset form.
- **BLOCKER-fork-pins**: The .env pinned blocks (ARBITRUM_FORK_BLOCK=510044719, ROBINHOOD_FORK_BLOCK=75699968) are no longer served by the public RPCs, which are non-archive (Robinhood always fails; Arbitrum only works on some nodes). Any fork test pinned to them fails with 'historical state ... is not available'. Code: The tests keep vm.createSelectFork(rpc, vm.envUint(block)). They were validated with env overrides ARBITRUM_FORK_BLOCK=510065249 and ROBINHOOD_FORK_BLOCK=75753211 (9/9 pass). The coordinator must re-pin .env or supply an archive RPC.

### Final verifier findings (verdict pass)

- [minor] AcrossBridgeAdapter.sol:100 Deliberate deviation from the literal spec (which said `address(uint160(uint256(req.recipient)))`): a recipient word with bits above 160 is rejected with InvalidParty instead of being truncated. This is the safer reading of DEC-087 (never deliver to an address the vault did not fix) and is documented in NatSpec, the commit message and a fuzz test. However the frozen interface documents InvalidParty as 'Recipient or depositor is zero', so the error now carries a meaning its NatSpec does not state. Suggested: Keep the rejection. When the interfaces are next unfrozen, widen the IBridgeAdapter.InvalidParty NatSpec to 'Recipient is zero or not a 20-byte EVM address, or depositor is zero' (interface doc change only, no ABI change).
- [minor] AcrossBridgeAdapter.sol:62 The constructor makes an external call to `fillDeadlineBuffer()` on the SpokePool and reverts when it is below 21,600 s. Not in the spec; harmless for CREATE2 address determinism, and it has the useful side effect of refusing a target without code (verified by test). It is a snapshot guarantee only: the SpokePools are UUPS proxies, so a later buffer decrease makes every send revert atomically (documented). It also means FundFactory deployments for new funds fail if Across governance ever lowers the buffer, which is the correct fail-closed behaviour but should be known to the factory author. Suggested: No change. Make sure the FundFactory module surfaces FillDeadlineBufferTooShort as a deployment-time revert reason rather than swallowing it.

## aave-v3-adapter

### Interface changes requested by builders


### Open questions raised by builders

- **AAVE-1 (DEC-068/DEC-079 reading)**: Meaning of the decreasePosition amount: principal to remove (income realized on top, the Uniswap V4 analog where any liquidity change realizes all fees) versus total asset amount withdrawn with income taken first. Code: params = abi.encode(uint256 principalAmount); type(uint256).max = all principal. Every decrease withdraws principalAmount plus the whole income measured at that block and returns principal0 = principalAmount, income0 = income. Above the current principal reverts AmountAbovePrincipal; zero reverts ZeroAmount; the key stays open (possibly empty) until closePosition.
- **AAVE-2 (DEC-080 vs spec 'empty params')**: Empty params on openPosition/increasePosition supply 'the whole transferred amount', which can only be read with balanceOf(adapter); raw USDC donated to the adapter would then be supplied and reported as used0/principal. Code: Implemented as specified (empty params = adapter's whole asset balance). With an explicit amount, any excess balance is returned to the vault unreported. Recommendation: the Spoke Vault always passes abi.encode(amount).
- **AAVE-3 (rounding loss owner)**: Aave's scaled arithmetic (live pool rounds the mint down) loses up to ceil(index/1e27) units per supply/withdraw; no decision says whether principal or income bears it. Code: Principal bears it: positionValue reports principal0 = min(principal, value) and income0 = value - principal0, so the first interest after an operation restores principal before counting as income; income never regresses. A unit Aave rounds in the fund's favour on a full exit is reported as income.
- **AAVE-4 (donated aTokens on full exit)**: Full exit uses Aave's withdraw(type(uint256).max) so no scaled dust stays behind; donated aTokens are therefore withdrawn too, and if the reserve is short of liquidity a donation can make close revert where the fund's own share alone would be serviceable (the donor loses the donation). Code: closePosition / decrease(max) withdraw the whole aToken balance, report only the ledger's pro-rata share (received * ledgerScaled / heldScaled) and pay the rest to the vault unreported for the garbage collector. decreasePosition with an explicit amount below principal still works in that situation.
- **AAVE-5 (increase needs liquidity for the income)**: Increase realizes the measured income by withdrawing it, so it needs reserve liquidity for that income (after the new supply is added). Code: increasePosition supplies first, then withdraws the income to the vault; if the reserve cannot pay the income the increase reverts (entry verb only; exits unaffected).

### Final verifier findings (verdict pass)

- [major] AaveV3Adapter.sol:364 `_supply` sizes the supply from `IERC20(asset).balanceOf(address(this))`. With empty `params` (spec: "empty to supply the whole transferred amount") that balance becomes `used0` and `l.principal`, so a stranger's 1-unit USDC donation to the adapter is reported to the vault as principal and `used0` exceeds what the vault transferred (a value base derived from `balanceOf`, which the hard rule and DEC-080 forbid). Demonstrated by test_DEC080_openWithEmptyParamsReportsDonatedAssetAsPrincipal (used0 == sent + 1). If the vault computes `sent - used0` this is also a 1-wei griefing DoS of the empty-params entry path. The explicit-amount path is safe: the surplus is returned to the vault unreported (test_DEC080_donatedAssetWithExplicitAmountGoesBackUnreported). The author followed the module spec, so this is a spec contradiction rather than an author error. Suggested: Drop the empty-params branch: require `abi.encode(uint256 amount)` on openPosition/increasePosition and keep `balanceOf` only as a sufficiency check (`amount > transferred` reverts), returning `transferred - amount` to the vault as today. If the empty-params path must stay, the Spoke Vault must always pass an explicit amount and never rely on it; state that in the adapter NatSpec.
- [major] AaveV3Adapter.sol:333 Every exit verb withdraws the whole pending income on top of the principal asked (`_withdraw(asset, l, principalAmount + income)`; `collectIncome` withdraws `income`; `increasePosition` withdraws `income0` after the supply). Once the reserve's available liquidity is below the pending income (100% utilization spikes do happen on Arbitrum USDC), `decreasePosition(1)`, `collectIncome`, `closePosition` and `increasePosition` all revert, so no unit of principal can be served although the reserve still has liquidity: DEC-068's "if a position cannot be served, pay what is possible" has nothing to pay with, and the vault has no verb to work around it. Also, `params` of decreasePosition is a principal amount, not the spec's "asset amount", so the amount the vault must budget against available liquidity is `available - pendingIncome`. Demonstrated on the mock (test_DEC068_pendingIncomeAboveReserveLiquidityLocksEveryExit) and on the real pool at the pinned block (test_DEC068_fork_pendingIncomeAboveReserveLiquidityLocksExits). Suggested: Make decreasePosition withdraw only `principalAmount` and leave the measured income in place (income stays `value - principal`, cumulativeIncome unchanged, DEC-064 is not affected since nothing is reinvested by the contract); let collectIncome remain the only verb that withdraws income, and let increasePosition skip the income withdrawal (report income0 = 0, income stays pending) or accept a flag in params. Alternatively keep the design but document that a Partial Payout under low liquidity requires the vault to call decreasePosition with `available - pendingIncome`, and accept that below `pendingIncome` of liquidity nothing can be served.
- [minor] AaveV3Adapter.sol:236 Checks-effects-interactions is loosely followed: `l.open = false` is written after `_exit` (which calls `pool.withdraw`), and `l.principal`/`l.scaledBalance` are updated after `pool.supply`/`pool.withdraw` in `_supply`/`_withdraw`/`increasePosition`/`openPosition` (the slither reentrancy-no-eth results). The post-call ledger writes are inherent (they use the scaled delta Aave produced) and every entry is `nonReentrant` + `onlyVault` against fixed Aave contracts, so this is not exploitable (test_DEC053_reentrantVaultDuringWithdrawalIsRejected and ...DuringSupplyRefundIsRejected confirm the guard for all five verbs), but `l.open = false` can move before the interaction at no cost. Suggested: Set `l.open = false` before calling `_exit` in closePosition; keep the rest and note the reasoning in NatSpec so the slither results are documented as accepted.
- [minor] AaveV3Adapter.sol:326 `lastIndex` is written on every verb (an SSTORE each) but never read by the income arithmetic; income is `value - principal` (`_split`), not `scaledBalance * (indexNow - indexLast) / 1e27` as the frozen IAdapter NatSpec for cumulativeIncome states. The two differ by Aave's mint rounding loss (up to ceil(index/1e27) units per supply, borne by principal in this implementation, confirmed on the live pool by test_DEC068_fork_liveRoundingMatchesLedgerAssumptions). The choice is conservative for income and monotonic, so no rule is broken; the field is informational only. Suggested: Either document in the struct NatSpec that `lastIndex` is informational (for off-chain reconciliation) and not part of the income formula, or drop it; note the rounding-loss-to-principal convention in cumulativeIncome's NatSpec.
- [minor] AaveV3Adapter.sol:387 `_withdraw` clamps the ledger to zero when the burned scaled delta exceeds `l.scaledBalance` instead of reverting. With the current invariants (the adapter never asks Aave for more than the ledger's value, foreign aTokens only add to the balance) this branch is unreachable, but if it ever fired it would silently zero the scaled ledger while `principal` stays positive, turning the position into an unreadable one rather than surfacing the broken accounting. Suggested: Replace the clamp with a custom error revert (e.g. `LedgerUnderflow(burned, scaledBalance)`), consistent with `UnexpectedWithdrawnAmount`'s never-silent stance.
- [minor] AaveV3Adapter.sol:366 Slither low-impact results judged as false positives or accepted: incorrect-equality on `amount == 0` (a zero check); uninitialized-local `count` in positionKeys (default 0 by design); calls-loop in the constructor (bounded closed list of reserve assets, DEC-053); cache-array-length in positionKeys (view, negligible). No change required. Suggested: None required; optionally cache `_assets.length` in positionKeys.

## uniswap-v4-adapter

### Interface changes requested by builders


### Open questions raised by builders

- **DEC-079 OPEN / OQ-12 (hooked pools)**: Uniswap V4 pools whose hooks charge on withdrawal would create a third value alongside principal and income. Code: A hooked PoolKey may appear in the constructor list, but it is never operable: poolTokens, openPosition and swapExactInput revert UnknownPool, so the Spoke Vault's creation check rejects it. Native-currency pools revert InvalidPoolKey at construction.
- **FV-16 (V4 donate)**: PoolManager.donate raises feeGrowthGlobal, so a third party (including a single-LP self-donation) can inflate what the adapter reports as income. Code: Donations are counted as income, because the pool's own accounting puts them into feeGrowthInside. No filtering.
- **OQ-04 (swap verb)**: Whether a swap is an entry or an exit verb, and who bears its Market Costs. Code: Follows the OPEN-QUESTIONS stance: blocked when deprecated, not when paused. A swap that stops at the price limit before using all of amountIn reverts PartialSwap, so the vault's debit of amountIn is always exact.
- **Q17-2a (collect under quarantine)**: Whether a quarantine should also suspend income collection. Code: MVP reading C1: collectIncome is never gated.
- **Spec wording: Permit2 approval**: The spec says 'approve Permit2 once'. The frozen IAdapter says the adapter clears every approval it grants (forceApprove to zero). Code: The frozen interface wins. For each operation the adapter sets the ERC-20 allowance to Permit2 and the Permit2 allowance to the PositionManager to exactly the owed amount, and resets both to zero in the same call.
- **Q60 read-only reentrancy window**: During a collect, decrease or increase call, realizedIncome is already updated (checks-effects-interactions) while the pool still shows the income as uncollected. A view read of cumulativeIncome from inside that call would double-count it until the call returns. Code: Accepted. Hookless pools and the Mandate tokens (USDC, WETH, USDG) hand control to no third party mid-call. Flagged for the vault and report authors.

### Final verifier findings (verdict pass)

- [minor] UniswapV4Adapter.sol:499 swapExactInput never hands back a surplus: the vault's ISpokeVault flow transfers exactly amountIn, but if more ever arrives (over-send, or dust already sitting in the adapter) the excess stays in the adapter until the next openPosition/increasePosition on that token forwards it, which contradicts the IAdapter custody note that the adapter holds no idle balance between calls. Not reachable through the specified vault flow, hence minor. Suggested: After the unlock (and the InsufficientOutput check) call _returnUnused(tokenIn), mirroring _pay; cost is one balanceOf and it is not a value base (DEC-080).
- [minor] UniswapV4Adapter.sol:534 unlockCallback discards the amount returned by poolManager.settle() (slither unused-return). Safe today because the PoolManager's end-of-unlock CurrencyNotSettled check catches any mismatch, but a fee-on-transfer or rebasing token would surface as an opaque CurrencyNotSettled instead of a named error, which hurts debuggability. Suggested: uint256 paid = poolManager.settle(); if (paid != amountIn) revert PartialSwap(paid, amountIn); (or a dedicated error) so the failure path is explicit.
- [minor] UniswapV4Adapter.sol:288 cumulativeIncome(token) walks every open position with two StateView calls each (slither calls-loop). Fine for report building, but DEC-092 says the income mechanism must not read all positions on each user operation; the NatSpec does not warn the Spoke Vault author that this view is O(open positions) and belongs on the report/collect path only. Suggested: Add a @dev line stating the cost and that the vault must only call it when building a report or after a collect, never from a Shareholder path; optionally also note positionKeys() is manager-bounded.
- [minor] UniswapV4Adapter.sol:637 _grant/_revoke implement the ephemeral-approval rule of the IAdapter custody NatSpec (forceApprove, Permit2 allowance with expiration = block.timestamp, cleared in the same call) but carry no citation, unlike every other rule in the file; the module rule is that every rule cites its decision. Suggested: Add `/// @dev IAdapter custody: ephemeral allowance of exactly the owed amount, cleared in the same call (forceApprove to zero).` on _grant and _revoke.
- [minor] UniswapV4Adapter.t.sol:161 Two test names carry no decision or open-question id (test_unlockCallbackIsPoolManagerOnly at line 161, test_openRevertsAfterDeadline at line 262); the module rule is that test names carry the id. Suggested: Rename to test_DEC058_unlockCallbackIsPoolManagerOnly (vault-only surface, no foreign entry) and test_DEC079_openRevertsAfterDeadline (or the IAdapter params rule they exercise).

## report-receiver

### Interface changes requested by builders

- IPriceSource.maxPriceAge() has no token argument, but feeds have per-token heartbeats (spec asks for (token, aggregator, maxPriceAge) tuples). Implemented as the strictest feed age, plus a non-interface maxPriceAgeOf(token). Suggested change: maxPriceAge(address token), so the Core Vault's mint staleness check (CoreVaultBase._usdcValue) can use each feed's own bound.
- IValueReportReceiver has no fundId() or constructor contract; the fund id is a required constructor input (bytes32 fundId) so that ReportMismatch can be checked. It is exposed as a public getter on the implementation only. Consider adding fundId() to the interface for the factory and Core Vault cross-checks.

### Open questions raised by builders

- **Q57 (d)**: Variation band on accepted report values (2% proposed, never answered). Code: Immutable constructor parameter variationBandBps (must be <= 10,000), exposed by variationBandBps(), never enforced.
- **Q57 (b) / QB9**: Spoke pricing, and USD vs USDC and USDG parity. Code: Chainlink USD feeds are read as USDC (USD = USDC 1:1) and fixed tokens return 1e18 per base unit, so they must have 6 decimals (USDC, USDG). Token decimals are constructor input, because report tokens are Robinhood addresses that do not exist on the hub (Robinhood WETH is keyed to the Arbitrum ETH/USD feed in the fork test).
- **OQ-10 (Q57)**: Staleness bound per feed vs the single IPriceSource.maxPriceAge(). Code: Each feed has its own maxPriceAge (maxPriceAgeOf(token)). maxPriceAge() returns the strictest (smallest) configured feed age, or 0 when only fixed tokens are configured. A feed with a longer heartbeat is therefore judged stale earlier by mint paths, which is conservative.
- **Q66 / DEC-099 value**: Exact report lifetime per spoke. Code: Read from Mandate SpokeConfig.maxReportAge; tests use 1,588 s (research 1,587 s plus one 0.1 s block, rounded up).
- **DEC-099 reading (clock skew)**: A spoke report timestamp ahead of the hub clock. Code: Treated as age 0 (accepted and fresh) rather than reverting. The timestamp is written by the Mandate's own Spoke Vault from block.timestamp and arrives about 15 min later under finalized consistency, so this only absorbs small cross-chain skew.
- **Payload size / relayer gas (DEC-086 note, Q57 (c))**: Delivery gas budget. Code: The full payload is kept in storage bytes so latestReport can return the decoded report. The first delivery of a one-position report cost about 1.02M gas in-test, well above the research's 400k GAS_CAP; later deliveries overwrite slots that are already set. Worth a ruling if reimbursement caps are adopted.

### Open questions raised by builders

- **CV-OQ-1 (DEC-085 vs DEC-092/104)**: ReportCodec inFlightToHub entries do not say whether a spoke-to-hub transfer is Principal or Income, so the hub cannot keep income in flight home out of Share Assets. Code: Every uncredited inFlightToHub entry counts as In-flight Value in Share Assets and in the Spoke Cap return leg. Income sent home is therefore briefly counted in Share Assets and in the index until it arrives and moves to collectedIncome.
- **CV-OQ-2 (Q60 spoke income tokens)**: Spoke income counters are in spoke-chain token addresses (USDG, Robinhood WETH), which can never be paid in kind on the hub. Code: On report acceptance, each counter delta is priced into hub USDC through IPriceSource at that moment and recognized in the USDC index with fees booked. An unpriceable delta leaves the counter unchanged so the next report retries. Regressed or anomalous counters are skipped. Never reverts.
- **CV-OQ-3 (DEC-054 income token list)**: The closed list of hub income tokens cannot be derived from Mandate pool keys (they are hashes) without calling adapters. Code: CoreVaultConfig.incomeTokens is supplied by the factory (read from IAdapter.poolTokens); USDC is always registered first.
- **CV-OQ-4 (DEC-102 Payout Fee base)**: The docs say '2% on the requested amount', but partial payouts pay the request in pieces. Code: The Payout Fee and flow fee are taken on usdcGross of each execution (the amount actually paid out), so the fees across partials total 2% (plus the flow fee) of what was paid.
- **CV-OQ-5 (DEC-080 unmatched arrivals)**: Arrivals held apart (fabricated ids, or amounts above what a report listed) have no recovery path. A stranger can front-run a real id and displace up to their own contribution. Code: They are kept in unmatchedArrivals forever, outside every base and not sweepable. Matching credits Principal first, then Income, up to the listed amount; the excess stays held apart.
- **CV-OQ-6 (DEC-066 griefing)**: Anyone can donate to a transit's escrow. Taken literally, 'refund must be > 0' would let a 1-wei donation mark a filled transit as refunded. Code: recognizeRefund requires the fill deadline to have passed and can be called again after RefundRecognized. A later report listing the id still moves the transit to ArrivalConfirmed, so a spoke arrival is never treated as unknown.
- **CV-OQ-7 (DEC-056 unwind failure)**: The docs do not say what happens when the automatic unwind reverts. Code: The unwind is attempted whenever Idle is short, even with empty hints. A revert is caught with UnwindForPayoutFailed and the claim becomes a Partial Payout (or reverts InsufficientFreeIdle when nothing is payable).
- **CV-OQ-8 (Q60 (b) vs (c))**: When hub recognition runs. Code: Hub income is recognized inside every deposit, claimPayout, withdrawIncome, receiveCollectedIncome and decreaseManagerFee, reusing the hubSpokeVault.buildReport() that valuation already reads. Recognition is also available through permissionless recognizeHubIncome.
- **CV-OQ-9 (sweep ledger)**: The spec lists owed fees as a separate ledger item, but owed fees are claims paid out of the collected balance. Code: ledger(token) = collectedIncome + (USDC only) idle + operatingCash + unmatchedArrivals. Owed fees are not subtracted a second time.
- **CV-OQ-10 (fee payment order)**: Who is paid first when the collected balance cannot cover both owed fees. Code: payOwedFees pays the manager fee first, then the protocol slice, each capped by the collected balance.
- **CV-OQ-11 (DEC-061 minimum scope)**: Whether the first-deposit minimum applies only to the very first deposit ever, or whenever the supply is zero. Code: It applies whenever totalSupply == 0, including after every share was burned; the next mint captures any residual (existing DEC-061 residual flag).
- **CV-OQ-12 (DEC-041 insufficient cash)**: The MVP has no hub Operating Expense other than the top-up (spending is OPEN). Code: The top-up (topUp amount, capped at Free Idle) runs on deposit, claimPayout, sendToSpoke and allocateToHubSpokeVault. OperatingCashInsufficient is emitted whenever cash is below the floor, followed by OperatingExpensePaid(payer ShareAssets).
- **DEC-092-returnLeg-kind**: The spoke's pending return leg (ReportCodec.Report.inFlightToHub) carries no TransferKind, so the hub cannot tell a Principal transfer home (which must stay in Share Assets, DEC-085/DEC-104) from an Income transfer home (which must stay out, DEC-092). Code: Every inFlightToHub entry not yet credited counts in Share Assets and in the Spoke Cap. For an Income transfer, Share Price is overstated by the in-flight income until the fill, when it is credited to collectedIncome and the price returns to its earlier level. Pinned by test_DEC092_OPEN_incomeReturnLegCountsUntilTheReportCarriesItsKind; the Principal path is exact (test_DEC104_principalReturnLegKeepsSharePriceThroughTheFill).
- **QB11/QB10-refund-window**: A transit that was filled but attested expired only through the deadline + maxReportAge path (reports delayed) stays ExpiryAttested and in Share Assets until a report confirms it, because no Across refund can ever reach the escrow. Code: recognizeRefund reverts NoRefund until the escrow holds at least amountSent. A later report listing the id confirms ExpiryAttested -> ArrivalConfirmed. A donation of the full amount recognized as a refund still lets a later arrival confirm without an unknown-value deduction (test_DEC066_arrivalAfterFullDonationRefundStillConfirms).
- **CoreVaultLogic-external-library**: CoreVault (21,518 B) plus its logic (17,922 B) cannot fit in one contract, so CoreVaultLogic stays an external linked library called by DELEGATECALL. The spec asked for internal libraries or abstract bases. Code: Accepted explicitly. The factory must deploy the library once per chain and link it, so its address is part of each fund's CREATE2 init code hash and trust surface (immutable, no upgrade path). Library events and errors are declared in ICoreVaultExtensions, which CoreVault inherits, so the Core Vault ABI is complete. The alternative, a separate valuation contract called by CALL plus internal libraries, is the caller's decision.

### Open questions raised by builders

- **OQ-09**: When a send home stops being counted as in flight. The task stance and the MVP stance table in docs/OPEN-QUESTIONS.md disagree: the table says it stays in flight until recognizeRefund. Code: Follows the task stance: the send leaves inFlightToHub once its refund is recognized or once fillDeadline + maxReportAge has passed, and is then presumed filled. The Transit record stays in state Sent, so a refund that arrives later is still recognized and credited back to Unallocated Balance.
- **OQ-01**: Whether a spoke arrival is credited only when its id matches a transfer the fund sent. The docs stance says yes, but a spoke cannot see the hub's send list; ISpokeVault says to credit and let the hub confirm. Code: Credits every well-formed arrival: from the Across SpokePool, in the base token, with this fund's id and the hub as origin. The report carries ids and amounts (last 64) plus cumulativeReceived so the hub can exclude what it did not send. A repeated id adds to the same entry and is listed once.
- **DEC-096-trigger**: Which operations count as the 'next operation' that tops up Operating Cash, and whether 'top-up' is an amount to add or a target level. Spending Operating Cash is OPEN (doc 30). Code: The top-up runs at the start of openPosition, increasePosition, decreasePosition, closePosition, collectIncome, swapExactInput, sendToHub and recognizeRefund. Arrivals and report() do not trigger it. It adds min(topUp, Unallocated base token), never reverts, and nothing can spend Operating Cash yet.
- **DEC-105-block**: Robinhood Chain is an Arbitrum Orbit chain, where block.number returns an L1 block estimate rather than the L2 block. Any hub rule that compares a report's block with an unwind block on the spoke (DEC-105) needs a consistent source. Code: Report.blockNumber and the ReportPublished event use block.number; Report.timestamp uses block.timestamp. No ArbSys call, so unit tests stay chain-agnostic.
- **LC-45/QA3-unwind-hints**: unwindForPayout takes its exit parameters and swap minimums from caller hints, which the Core Vault forwards from the claimant. A claimant could set loose minimums and sandwich the unwind; that Market Cost falls on the fund. Code: Hints are accepted as given. A hint is required for every position visited (MissingUnwindHint), swaps must turn exit principal into USDC in a Mandate pool, and the adapter enforces minAmountOut. There is no price guard in the vault.
- **LC-22/LC-37/LC-49-spoke-income**: Income in a non-base token on a spoke (for example WETH fees) has no path home: swaps only take Unallocated Balance, and sendToHub only sends the base token. Code: Non-base income stays in the collected income bucket, is counted by cumulativeIncome and is never swept.
- **Q66-cumulativeSentHome**: Whether cumulativeSentHome should decrease when a send is refunded. Code: It only grows, on each send. A refund credits the ledger back and removes the transit from inFlightToHub; the hub reconciles through the list of ids.
- **Factory-CREATE2**: The Mandate's spokeVault address cannot be checked against address(this) inside a CREATE2 constructor that receives the Mandate (the address depends on the init code). Adapters must already be deployed so their codehash can be pinned and poolTokens called. The external library must be deployed and linked on each chain. Code: The constructor does not check spokeVault == address(this) or adapter.vault() == address(this). It requires adapter code to exist (AdapterHasNoCode) and chainId_ == block.chainid. SpokeCrossChainLib is linked at deploy time.

- [major] SpokeCrossChainLib.sol:25 SpokeCrossChainLib is an external linked library (external/public functions, deployed at 9,738 B): every sendToHub, recognizeRefund, report, buildReport and cumulativeIncome runs through DELEGATECALL into it, and the SpokeVault artifact carries 5 unresolved link references. This is not a proxy and the library is immutable, but it departs from the explicit instruction (internal libraries or abstract bases) and adds a deployment constraint: for the CREATE2 vault address to be identical on hub and spoke (DEC-054 factory) the library must sit at the same address on every chain, and the vault NatSpec that says 'no proxy, no upgrade path' does not disclose the delegatecall trust boundary. An inline split would not fit (20.9k + 9.7k > 24.5k), so this is a real design choice, not an oversight. Suggested: Either shrink the vault to fit inline (drop the non-interface views bridgeAdapters/poolTokens/arrivals/inFlightTransitIds, the buildReport assembly re-encode, and the memory Config rebuild), or keep the linked library and make it explicit: NatSpec the delegatecall boundary, deploy the library with CREATE2 at a chain-independent address, and have the factory pin/verify the library extcodehash the same way adapters are pinned (Q17-4).
- [major] SpokeVault.sol:424 Arrival ids are kept in a 64-slot ring (SpokeVaultTypes.ARRIVAL_WINDOW). Across passes no depositor, so a stranger can make 64 dust deposits with fresh ids (self-relayed, gas cost only) and evict a genuine hub-to-spoke id from every future report before the hub confirms it (new test test_OQ09_dustSpamEvictsAGenuineArrivalFromTheReportWindow). Per the ICoreVault.attestExpiry NatSpec, a report built after the deadline that does not list the transit is proof of non-arrival, so the hub would attest expiry of a transit that did arrive, and under the QB11 stance keep it in Share Assets until a refund that never comes, while the spoke's unallocated already counts the same money: a permanent double count. The implementation follows the module spec's '64-id window, presumed filled after fillDeadline + maxReportAge' wording, but docs/OPEN-QUESTIONS.md's binding OQ-09 row says 'Spoke keeps ids in the report until the hub confirms them; hub-bound transits stay in flight until recognizeRefund', so spec and binding docs disagree and the code follows the spec. Suggested: Reconcile the OQ-09 stance in docs and code. Safer options: never let absence from arrivedTransits serve as proof of non-arrival on the hub; confirm arrivals on the hub by ordering against the monotonic cumulativeReceived (stranger dust can only over-confirm, i.e. donate) rather than by id presence; or keep every unconfirmed id (no eviction) and bound the report by dropping only ids the hub has acknowledged once hub-to-spoke messaging exists.

- [minor] SpokeCrossChainLib.sol:70 recognizeRefund calls the escrow's release() before setting t.state = RefundRecognized and removing the in-flight entry. The escrow is the fund's own clone and the entry is nonReentrant, so it is not exploitable, but it is the one value path that is not checks-effects-interactions. Suggested: After a Decrease, drop the registry entry when the adapter no longer lists the key (adapter.positionKeys()) or reports liquidity == 0 and reverts on positionValue; and add a fitness test on the V4 adapter that a full decrease keeps the key open.
- [minor] SpokeVault.sol:143 On a spoke the constructor reads spoke.spokeToken and maxReportAge but never asserts address(this) == address(uint160(uint256(spoke.spokeVault))), the Mandate's registered report emitter and bridge recipient.
