**What this card changes in the plan (read first).**
1. **CF-V4-1, confirmed (probe).** `openPosition` takes the new position's key from `positionManager.nextTokenId()` (V4A:366) and only later lets token code run (`forceApprove` in `_grant`, V4A:670-671, 683). A token whose `approve` mints a third-party position through the permissionless PositionManager (PM:172-177, 353-369) shifts the id: the adapter records the third party's NFT and owns an unrecorded one. Observed: the fund paid 29.55e18 of each token into NFT 2, recorded key 1 (owned by the third party); `positionValue(1)` reported the third party's liquidity (5e21, then 5.5e22 after the third party added to it); `cumulativeIncome` fell from 54.99e18 to 0 when the third party collected its own fees; `closePosition(1)` reverts `NotApproved(adapter)` forever, and nothing in the adapter can reach NFT 2. Unreachable with USDC, WETH and USDG as they behave today (no code runs on `approve`); reachable for any Mandate pool whose token runs code on `approve` (fund creation is permissionless, DEC-001, and neither the adapter nor the factory restricts pool tokens). The property is INV-V4-10 (open keys are exactly the NFTs the adapter owns).
2. **CF-V4-2, cross-module liveness (reading).** Deprecation blocks `swapExactInput` (V4A:523, OQ-04 stance), and the Spoke Vault forces the position's own pool as the only swap route for a token paired with USDC (SV:883-887, a hint naming another route reverts `InvalidUnwindSwap`) and calls it without `try` (SV:905-921). So once the guardian deprecates a V4 adapter, every automatic unwind step of a WETH/USDC position reverts at its swap, and no fund path converts WETH to USDC (the manager swap is blocked too, pinned by `test/unit/spoke/SpokeVaultSpoke.t.sol:290-293` with `MockPositionAdapter`, which mirrors V4A:523 at `test/mocks/spoke/MockPositionAdapter.sol:218`). "Deprecated = withdraw-only" (DEC-058) holds for the adapter's verbs but not for the fund's exit in USDC. Founder decision (OQ-04, Q17-3, section 10.2).
3. **Exit liveness rests on bit-exact equality of the adapter's arithmetic with Uniswap's.** The adapter settles and takes explicit amounts it computed itself (V4A:40-46, 719-726), so a one-wei divergence in any reachable pool state makes every exit of that position revert permanently (`CurrencyNotSettled`, PMGR:111); there is no fallback exit. The unit tier cannot see a divergence: `MockV4` returns the pool-wide fee growth for every range (MV4:130-133) and re-implements the adapter's own formulas (MV4:197-230); the fork tier never moves the price outside the position's range (V4F:31-33: range of +-200 ticks, swings of 40). The most valuable new work is a **local real-V4 tier** (V4-W03): the real v4-core `Pool`, `Position`, `StateLibrary` and the real `StateView` all compile under 0.8.28 (`pragma ^0.8.0`, read), so a stateful invariant can drive the adapter through tick crossings, donations and fee-growth wraps without RPC.
4. **Formal verification reach.** Every verb is loop-free except the bounded plan copy (V4A:730, at most 5 actions); the obstacles are external calls and Q128 or `SqrtPriceMath` arithmetic, not control flow. Access control, the flag gating, the plan's closed vocabulary and destinations, the approval hygiene and the unwind sizing are unbounded-provable with summarised externals (section 9.2). The Uniswap-equivalence lemmas are bounded symbolic plus differential fuzz; Uniswap itself stays an assumption (section 9.4).
5. **Adversarial review (section 11) changed this card.** Two new defects were confirmed by execution in an isolated probe project (scratchpad `probe-v4-review/`, outside the clone, 2 tests passing): **CF-V4-10** a `poolManager` immutable that is not the manager of the PositionManager and StateView does *not* fail closed: positions open and close normally and every swap reverts, which freezes the unwind's conversion exactly like CF-V4-2; neither the adapter (V4A:218-221), the factory (FF:86-96, 102-105) nor the deploy script (`script/FactoryDeployment.sol:46-63`) checks the three addresses against each other, so the old INV-V4-41 was false as written. **CF-V4-11** a pool token whose issuer turns on a transfer fee after positions exist (USDC is an upgradeable proxy, A-TOKEN): exits succeed at the adapter but deliver less than the amounts returned (probe: 29.553e18 returned, 29.257e18 received), so the Spoke Vault's backing check reverts every exit and unwind step of that pool (SV:773-774, 972-977); the card had said a fee token "never loses funds" and only reverts entries. Also added: the interface promise that income never blocks principal (IA:131-143) is not met by this adapter (CF-V4-12, reading); a position NFT transferred to the adapter by anyone falsified the old INV-V4-10 (PM:549-552); the claimant's atomic sandwich of the unwind (card 02 T4) was judged too kindly in class 10; an exit liveness matrix (section 4.2, INV-V4-50) now covers every failing dependency. ### 3.3 Monotonic counters and state machines

Counters: `realizedIncome[t]` non-decreasing (only `+=`, V4A:661-662); `deprecated` false to true only (AG:44-45); `cumulativeIncome(t)` claimed non-decreasing (V4A:288-290, IA:192-198; Q60, DEC-092), a derived view that CF-V4-1 breaks (probe); PositionManager `nextTokenId` strictly increasing (PM:121, 365-368), which makes position keys unique.

Flag machine, states `(paused, deprecated)`: `setPaused(b)` moves `(p, d)` to `(b, d)` from any state; `deprecate()` moves `(p, false)` to `(p, true)` with an event and is a no-op on `(p, true)`. Position machine per key `k`: Absent, then Open at `openPosition` (V4A:368-369), Open under `increasePosition`, `decreasePosition` (which keeps `0 < L`, V4A:440), `collectIncome`, then Closed at `closePosition` (V4A:479-480), terminal. Closed keys are never reissued while `nextTokenId` is monotonic. Under CF-V4-1, "Open" can hold a key whose NFT another address owns, which makes the Open to Closed transition unreachable for that key. Added by review: `openPosition` ignores the return value of `_openPositions.add` (V4A:369) and writes `_positions[key]` unconditionally (V4A:368), so an id already open would overwrite that position's pool and ticks; this is excluded only by the strictly increasing `nextTokenId` (PM:121, 365-368; assumption A-V4-3), which is why the per-step form of INV-V4-11 is `conditional(A-V4-3)`. A foreign NFT sent to the adapter (surface fact d) never enters this machine.

Swap machine inside one call: `unlock` (V4A:535), callback `swap` then `sync`, transfer, `settle`, `take` (V4A:553-577), PoolManager end check that every delta is zero (PMGR:111). The adapter checks full fill twice (V4A:565, 576), so the vault's debit of `amountIn` is exact.

### 5.3 Gaps

1. No stateful invariant and no symbolic spec for the adapter (`02-BASELINE.md:370`).
2. Real Uniswap arithmetic is never exercised off range: the mock's fee growth ignores ticks, and the fork swings stay inside the range (CF-V4-9). Exit exactness after a tick crossing, at the tick boundaries and after other LPs flip the same ticks is untested.
3. No hostile-token actor that calls the PositionManager or reads views mid-call (CF-V4-1, CF-V4-5); no fee-on-transfer, rebasing, pausing or blacklisting token (V4A:576, CF-V4-6).

5. `increasePosition` from desired amounts (`liquidity == 0`, V4A:399-400) is never called; decrease and close after their deadline are never tested (only open V4T:262-267 and swap V4T:535-548).
6. Events: none asserted in the v4 suites; typed `AmountBelowMinimum` never asserted.

8. NFT custody is asserted only at open on a fork (V4F:253) and after burn (V4F:257-258), never as a lifecycle invariant (every open key is an NFT the adapter owns and nothing else is).
9. No gas curve for `cumulativeIncome` and `positionKeys` against N open positions on the real StateView (input for `02-spoke-vault.md` T3).
10. (Added by review.) Nothing tests the wiring of the three Uniswap addresses against each other (CF-V4-10), a fee switched on after open (CF-V4-11), income failing while principal is due (CF-V4-12), or an NFT sent to the adapter by a third party (INV-V4-49); no test asserts that a repeated `deprecate()` emits nothing; there is no per-cell exit liveness test (section 4.2).

## 9. Formal verification readiness

### 9.1 Strategy: a guard prefix, a pure core, a pure plan, and one conformance check

Every verb decomposes into four parts, each with its own tool. (a) **Guard prefix**: `onlyVault` (V4A:198), the guard, the flag gate (AG:50-53, V4A:523), registry or key membership (V4A:586-594), parameter decoding; no external call happens before its last possible revert, so these properties need no protocol model at all. (b) **Arithmetic core**: `_uncollectedIncome` (V4A:598-615), `_principal` (V4A:621-637), `_liquidityForAmounts` (V4A:639-652), unwind sizing (V4A:325-327), the quote (V4A:336-339): pure functions of at most 8 words once the StateView answers are symbolic, sharing `SqrtPriceMath`, `TickMath` and `LiquidityAmounts` code with Uniswap, and repeating `Position.update`'s expression literally (V4A:612-613 against POS:93-96). (c) **Plan builder**: `_newPlan`, `_push`, `_pushSettle`, `_pushTake`, `_pushRealizeIncome`, `_execute` (V4A:700-734), pure apart from reading the `vault` immutable, at most 5 actions in a fixed order per verb. (d) **Effects**: one `modifyLiquidities` or `unlock` call and the token calls, summarised by the `SymV4` model of 9.5, whose conformance checker recomputes with the real v4-core libraries the caller deltas the plan implies and asserts they net to zero. With (d), "the plan passes the PoolManager's end check" (PMGR:111), the consequence of INV-V4-20 that exit liveness hangs on, becomes a single-transaction property.

Properties over sequences close by induction, not by depth: per step, a realization moves exactly the realized amount from the uncollected term to `realizedIncome` (18 per step), an open key's uncollected term cannot shrink between steps while its fee growth inside is non-decreasing (assumption A-V4-1 for a range with liquidity), and closing removes a key whose uncollected term was just realized; together they give INV-V4-19 for every sequence. INV-V4-10 needs one more per-step fact, "the NFT minted in `openPosition` is the recorded key", which is false under CF-V4-1 and true under R1 of 9.6. The invariant harness (V4-W05) checks that this lemma set is complete, since a missing lemma shows up there as a counterexample.
