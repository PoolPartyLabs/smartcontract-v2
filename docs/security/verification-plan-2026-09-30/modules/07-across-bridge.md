**What this card changes in the plan** (read first):

1. **The adapter is the most provable contract in the system, and the Across protocol is the least.** AB is a loop-free, storage-free (apart from two guardian flags) call builder with one `STATICCALL` and no `CALL`; 20 of the 35 original properties of section 6 (39 after the review) are single-call specifications a symbolic tool can close, 16 of them unbounded (P). What cannot be proven is what the fund relies on most: that the live SpokePool delivers exactly `outputAmount`, refunds exactly `inputAmount` to the escrow, and keeps accepting deposits. ### 3.2 Divisions and rounding

There is no division, multiplication or rounding in AB, AG or TM. The only arithmetic is `uint32(block.timestamp) + FILL_DEADLINE_SECONDS` (AB:104): the cast truncates silently, the addition is checked. Consequences: for `block.timestamp` in `(2^32 - 1 - 21,600, 2^32)` the build reverts with Panic 0x11 (UA:113-121); from `2^32` on the truncated value wraps and the build returns a deadline in the past without reverting (P4: at `2^32 + 101` it returned 21,700), except in the top 21,600 s of every later `2^32` period, where `(block.timestamp mod 2^32) + 21,600` overflows again and the build panics (review precision, same arithmetic). The hub rejects such a call (`call.fillDeadline <= block.timestamp`, CVL:596); the spoke does not (SCL:262-266), and the pool would not either: `_depositV3` checks only `fillDeadline > currentTime + fillDeadlineBuffer` (SP:1405), so the lower bound the vendored NatSpec states (IAS:35-36) does not exist on chain (AB-17). Year 2106, informational (AB-4).

Review check of the rounding directions: confirmed. AB, AG and TM have no division; the two vault divisions floor `maxFee` (CVL:660, SCL:221), so the allowed fee is never looser than the Mandate. One nuance added to AB-7: the fee check is the only guard against a decimals mismatch where the input token has more decimals than the output (the output is then numerically far below the input and AB:96 passes it), and `maxBridgeFeeBps` may be as high as 10,000 (`src/mandate/Mandate.sol:176`), so "fail-closed" holds only while `maxBridgeFeeBps` is below the implied fee; the factory's token pins (FF:151, FF:201) keep it unreachable for USDC and USDG.

The two divisions that bound what crosses the bridge are in the vaults, cited here because INV-BRIDGE-30 composes with them: hub `maxFee = usdcAmount * maxBridgeFeeBps / BPS` (CVL:660) and spoke `maxFee = amount * maxBridgeFeeBps / BPS` (SCL:221), both floor, so the allowed fee is never looser than the Mandate: rounding favours the fund. The hub computes `fee = outputAmount < usdcAmount ? usdcAmount - outputAmount : 0` (CVL:661), so on the hub an output above the input passes the fee check and only AB:96 rejects it (AB-10).

## 9. Formal verification readiness

Strategy. AB has no state apart from two guardian bits, so every property of the builder is a one-call property over a fully symbolic pre-state (both bits symbolic, immutables symbolic, pool counter symbolic): a one-call proof is already unbounded in time, and the only bounds are on the message length. TM is pure. The vault side (DELEGATECALL libraries, clones, ledgers) stays in cards 01 and 02; compositions with a vault (INV-BRIDGE-18, -29) use the harness vault MHV, which follows IBA's custody rules, or the `verify` profile with pre-linked libraries (`01-TOOLING.md` 7.7). Across itself is never verified: its behaviour enters as assumptions (9.3), each tied to a fork test or an open question.

**Review alignment with the final preparation document.** Technique letters map to its tiers (`03-FORMAL-VERIFICATION-PREPARATION.md` section 1.1): P is V3 (V3-bv on the loop-free AB and TM checks, V3-k under Kontrol; V4 for the AdapterGuard flags, whose only writers are the two guardian verbs), S is V2 with the bound printed in the label, C is V0, U, F, I and K are V1, and the FLAGGED and ASSUMED labels are as defined there. ### 9.4 Obstacles in the current code

- **Optimizer dependence** (AB:107-125): the file compiles only with the optimizer on or via-IR (`02-BASELINE.md` section 3.1). Every tool must build with the default or `verify` profile; any tool that recompiles with solc defaults (Manticore, Mythril, some crytic-compile invocations) fails on this file; Scribble's instrumentation adds locals to the same function and is likely to fail. **Review correction:** R1 does not remove the obstacle (P13: the split still fails without the optimizer, because the 12-value ABI encoder is itself too deep); R1b does (P13).
- **Dynamic `bytes` inside the calldata struct**: `SendRequest.message` (IBA:54). Halmos needs concrete lengths (the 1 `MCOPY` must have a concrete size), hevm explores up to `--max-dyn-size`, Kontrol needs a concrete length or ABI lemmas for a symbolic one. Taken per length (9.2).
- **Byte equality of encoded calldata**: compare decoded words or word loads (as UA:67-75 does with memory word loads through `_word`, UA:52-56; review correction of the citation, which read "UT:67-75 ... calldata slices"), not `keccak256` of symbolic memory (uninterpreted in hevm, `01-TOOLING.md` 5.11).
- **External calls needing summaries**: the constructor's `fillDeadlineBuffer()` (AB:62) and the build's `numberOfDeposits()` (AB:126), both views: a one-slot model with a symbolic return and a revert flag.
- **Immutables**: Kontrol needs `--symbolic-immutables`; hevm equivalence compares immutables as zero placeholders (`01-TOOLING.md` 8.10), acceptable for R1 because both builds carry the same immutables.
- **Timestamp truncation** (AB:104): properties need the case split of -06.
- Absent here: loops with data-dependent bounds, DELEGATECALL, assembly, `mulDiv` or Q128 arithmetic, create or clone operations, mappings of structs. TM's `abi.decode` of a memory `bytes` is the only decoding (TM:40-43).
