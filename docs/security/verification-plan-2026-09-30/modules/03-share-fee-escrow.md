**What this card changes in the plan (read first).**
1. Two liveness defects are confirmed by execution. **SF-1**: the Core Vault's registry read (CVL:401-408) does not catch a codeless registry, a return value above `uint16` or short return data (probe: all three revert instead of falling back to 5,000), and the factory only checks that the registry address is non-zero (FF:146), so a mis-wired registry blocks every income collection of every fund of that factory for good (immutable at FF:57,107 and CVB:39). **SF-2**: a `ManagerFeeVault` that cannot receive a token (issuer blacklist or pause) makes every collection of that token revert: hub forwarding, the Across fill of listed Income, and delivery of any report that credits held Income (probe: all three revert with the token's reason), which also stops fresh reports and therefore mints. Exits keep working (probe: a full Instant exit succeeds). Only the manager can unblock, by an irreversible cut of the performance fee to 0 (CVI:64-73, DEC-110).
2. One suspected griefing vector is refuted by execution: starving the registry read of gas cannot force the default slice (probe: 829 of 1,140 gas limits between 30,000 and 600,000 succeeded, all at the stored 1,000 bps slice; warm-access caveat in section 10).
3. This module is the cheapest formal-verification target in the repository: no loops, no linked library, no DELEGATECALL, no time dependence, no arithmetic beyond `%` and OZ `_update`. 21 of the original 45 properties are provable for all inputs and states in this module (V4 targets of `03-FORMAL-VERIFICATION-PREPARATION.md` 1.4; INV-SHARE-29 is proven as INV-CORE-50 on the real code). 4. Adversarial review (section 11, 2026-09-30): SF-2's "exits keep working" holds only for a block of the MFV address, not for an issuer pause (the full-burn income payment CVI:46-57 reverts, core CF-2), and "only the manager can unblock" is no remedy when the manager is sanctioned or keyless; the report path is affected only for USDC (CVL:525). ### 3.2 Divisions and rounding

No division and no multiplication exists in the four contracts; the only arithmetic is `amount % WHOLE_SHARE` (ST:48, :56, exact) and OZ `_update` additions and subtractions (`ERC20.sol:179` checked; `:185-199` unchecked, section 4 row 13). The divisions that consume this module's outputs are in CVL and owned by `01-core-vault.md` (INV-CORE-50); they matter here because they fix what reaches MFV:

| Site | Expression | Direction | Who it favours |
|---|---|---|---|
| CVL:388 | `managerFee = amount * performanceFeeBps / BPS` | floor | holders (the fee is never above its exact value) |
| CVL:389-390 | `slice = managerFee * sliceBps / BPS`; `managerFee -= slice` | floor on the slice | manager against the protocol (MFV gets `fee - floor(fee * s / 1e4)`, at most 1 base unit above its exact share per collection) |
| CVL:391 | `net = amount - managerFee - slice` = `amount - floor(amount * perf / 1e4)` | exact remainder | holders; independent of `sliceBps` (INV-SHARE-29) |
| CVL:404 | `bps = value > BPS ? BPS : value` | cap | only reachable with a non-MR registry (MR caps at 5,000) |

The whole-share floor of mints and burns is in `ShareMath` (`01-core-vault.md` section 3.3); ShareToken only enforces it (ST:48, :56).

### 9.5 Proposed harness (W05)

- **Concrete:** ST deployed with `coreVault` = a fixed address the check pranks as; MR with a fixed owner; the TE implementation and clones made with `Clones.clone`; MFV with fixed `fund` and `manager`; one instance of the shared `test/harness/models/SymToken.sol` per contract that holds tokens (review: the model is shared by every module, FV preparation 4.6, not a share-local file).
- **Slots (review):** injections use the generated `test/harness/slots/Slots<Contract>.sol` maps, each proven by `SlotMap.t.sol` (FV preparation 4.4, P-08), never the hand-written offsets below, which only document what the generator must reproduce; the packed MR word goes through a pack-and-range helper (FV preparation 4.3).
- **Guard (review):** on the symbolic-storage routes (`hcheck_`, `prove_`) the MFV guard word at `0x9b779b17...c55f00` must be constrained to 1 in WF-MFV, or every `withdraw` path reverts and the proof is vacuous (FV preparation 4.3, 8.2 item V7).

- **Any-selector properties (02, 13, 24, 35):** one check per known selector with symbolic arguments, plus one check with a symbolic 4-byte selector constrained outside the known set (fixed calldata length, as Halmos requires [S10]) that must revert.
- **Ghosts:** none in storage; pre and post reads inside each check; one untouched symbolic key read before and after for every frame lemma.
- **Assertions:** `assert` (Panic 0x01 is the failure signal for Halmos [S10]); revert expectations through a low-level `call` and its `success` flag, never `expectRevert` (`01-TOOLING.md` 7.3).
- **Runners:** the same files under Halmos (`^check_`), `forge test --symbolic`, `hevm test --prefix check` on the `verify` build (review correction: the first version said no pre-link was needed; section 7) and Kontrol (W11).
