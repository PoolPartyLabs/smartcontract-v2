**What this card changes in the plan** (read first):

1. **The factory holds no value and sits on no exit path**: no contract in `src/` calls it after creation (grep of `isFund`, `fundByNumber`, `IFundFactory` outside `src/factory`: 0 hits), it has no owner, pause or setter (FF:29-30), and its runtime can only write three slots (FF:163-165). Its defensive job is the binding **Mandate to addresses to code**. Two links of that binding are weaker than the documentation says, both reproduced: FF-1, a code-store chunk that is not an inert `0x00`-prefixed data contract is accepted and its hash recorded (P2), so `creationCodeHash(role)` proves nothing about what a later deployment reads unless chunk immutability is checked off chain; FF-2, `coreVaultLogic` and `spokeCrossChainLib` are informational (P3): nothing on chain ties them to the libraries linked inside the pinned code. Both close with a release gate (W8) and, if the founder wants it on chain, a one-line check each (section 9.6).
2. **Unit tests run without mainnet size limits** (fork tests share the forge EVM configuration; Not verified for them): forge lifts EIP-170 and EIP-3860 by default (I1: a 100,000-byte initcode deploys), and setting `code_size_limit = 24576` stops the test contracts themselves from deploying. Size bounds must be asserted explicitly (W7). Measured in the unit fixture (P1): a Mandate with 57 hub Uniswap V4 pools creates within 32M gas (Arbitrum One's per-transaction limit per DEP:102), 61 (60 extra) fail `OutOfGas` at the Core Vault's code deposit with **empty revert data**; about 0.2M gas per extra pool. The EIP-3860 limit would bind later (section 4.1, FF-4). This is the upper bound the core and spoke cards should use for exit-loop gas.
3. **Cross-module gap FF-5**: nothing stops the hub from sending to a spoke whose Spoke Vault does not exist yet, or can never exist (CVL:638-668 has no existence gate; V2:210 shows a hub Mandate naming an uncreatable spoke). Owned by the core card; the factory's predictable addresses make it reachable.
4. **Formal verification here is split by design**: the pure derivations (salts, fund ids, CREATE2 and CREATE addresses) and the loop-free guard prefixes of both creation functions are unbounded proof targets; the deployment path (CREATE2 plus a CALL whose init code carries the ABI-encoded Mandate, 30 to 65 KB of concrete code per fund) is not, and is covered by a stub-code factory under bounded symbolic execution (W11), stateful fuzzing (W6, W12) and fork tests. Corrected in review (section 11), aligned with `03-FORMAL-VERIFICATION-PREPARATION.md` section 1.4: of the 44 properties of section 6, 12 are V3 or V4 targets (01, 02, 03, 05, 06, 07, 12, 13 as a write-once step raised from V1 by this review so the factory meets the FV-complete rule of 03 section 1.1, 16, 37, and the createFund halves of 24 and 38), 23 only after refactor R1; 8 are V2 bounded (09, 10, 14, 18, 19, 21, 22, 25); 5 are V0 structural (04, 28, 31, 39, 41); the rest are V1, release gates or FLAGGED pins. The card first claimed 19 unbounded targets, counting V0 opcode facts, a semantic argument (15) and two bounded rows (18, 25) as proofs.
5. **Adversarial review (section 11) added five findings (FF-10 to FF-14) and corrected three (FF-1, FF-5, FF-9).** The most serious: FF-10, the operator key can place arbitrary code at every fund address on any chain where the canonical factory is not yet deployed, so a fund naming such a chain trusts the operator key as its report emitter and bridge recipient; FF-1 is broader than stated, an EIP-7702-delegated EOA used as a code-store chunk changes the deployed bytes in any later transaction (EIP-7702 is Final and active on Arbitrum One through ArbOS 40); FF-5 is confirmed from Across source: a fill to a Spoke Vault address without code delivers the tokens and skips the message, and after `createSpoke` anyone sweeps them to the Protocol Recipient (SV:556-563). Also added: FF-11 (the Manager is an address, so a contract-wallet Manager may not control the same address on a spoke), FF-12 (the Protocol Recipient, guardian, price source and registry are shared immutables of every fund, so one USDC blacklist blocks exits in all funds, core card CF-3), FF-13 (the hub accepts spokes that can never be created), FF-14 (the `wormholeChainId` check the factory can do locally, report card CF-R11).

### 9.4 Obstacles in the current code

- CREATE2 then a CALL whose calldata is stored code plus the ABI-encoded Mandate (C3:45, :48; FF:478, :509): symbolic init code gives partial exploration in hevm (`01-TOOLING.md` section 5.11); Halmos and KEVM behaviour with symbolic init code Not verified. Answered by stubs and concrete Mandates on the success path.
- Size of the real path: one `createFund` executes about 33 KB (Core Vault) plus 32.6 KB (Spoke Vault) of constructor code and about 21M gas in the unit fixture (P1); infeasible symbolically.
- ABI decoding of a Mandate with six dynamic arrays of structs plus `bytes` of 34 KB (IFF:104-108): fixed lengths; the code bytes stay concrete.
- Data-dependent loops: FF:244, :315, :323, :330, :387, :418, :485, :499, plus `MandateLib` loops in the child constructors (SV:143, CVB:69), which the stubs skip.
- Private helpers (FF:127, :275-335, :345-510) cannot be called from a test subclass: R1.
- Keccak everywhere (salts, fund ids, `m.hash()`, code hashes): uninterpreted in hevm, possible unreproducible counterexamples (`01-TOOLING.md` section 5.11).
- Assembly: 7 blocks (C3:44-46, :50-52; FF:424-426, :492-494; CS:36-38, :44-46, :65-67); their memory-safety claims go to `forge test --brutalize` and Wake, not to the provers.
- Chain id: hevm has no `vm.chainId` (`01-TOOLING.md` section 7.4); make `m.hubChainId` the symbolic side of FF:145 and FF:197.
- Two chains, one address (added in review): one EVM state cannot hold the hub factory and a spoke factory with other wiring at the same address, and UT only alternates them through a snapshot revert (UT:98-102). Cross-chain properties (the hub prediction equals the spoke deployment, INV-FACTORY-08 across chains, 10 across chains, 43) are therefore V1 (W1 mode (a), fork FK:79) and never enter a symbolic check; per-chain properties are unaffected.
- Not obstacles: no DELEGATECALL and no linked library in FF or C3D, no nonlinear arithmetic, no Q128 index, no report decoding, no time dependence; the transient guard's TLOAD and TSTORE are supported by Halmos, hevm and KEVM (`01-TOOLING.md` section 4.2).
