### 3.3 State machines and their legal transitions

1. **Hub-bound transit, per `transitId`** (spoke role). States from `TransitState` (`src/interfaces/FundTypes.sol:13-19`); only three are reachable here:
   - `None -> Sent`: `sendToHub` only (SCL:291-292), with a fresh id (SCL:50) and a fresh escrow (SCL:51). `fillDeadline` and `bridgeRef` are copied from the bridge adapter's return (SCL:287, :289), not computed by the vault; the Across adapter sets `uint32(block.timestamp) + 21_600` and encodes the same value in the call (`src/adapters/AcrossBridgeAdapter.sol:104`, `:128`). The vault checks neither against the calldata (T11), and the refund gate (SCL:76) and the pruning time (SCL:301) both key on it.
   - `Sent -> RefundRecognized`: `recognizeRefund` only, after `fillDeadline` (SCL:76) and when the escrow holds at least `amountSent` (SCL:81).
   - `ArrivalConfirmed` and `ExpiryAttested` are hub-side states and are never written here. `RefundRecognized` is terminal.
   - In-flight list membership is a separate sub-state: added at send (SCL:293), removed at refund (SCL:83) or by report pruning once `block.timestamp > fillDeadline + maxReportAge` (SCL:103-106, :300-302). A pruned transit stays `Sent` and can still be refunded (`docs/OPEN-QUESTIONS.md:53`). Membership grows by one per send whatever the amount (the only lower bound is `amount > 0`, SCL:216); a filled send leaves the list only by pruning, which happens only inside `report()` and walks the whole list in one call (SCL:103-106), so the list size is a liveness parameter of `report()` (T13).
2. **Position registry, per `(adapter, positionKey)`**: absent (slot 0) -> registered (SV:266-267; a duplicate reverts SV:263-264) -> removed only by `closePosition` or an unwind close when the adapter no longer lists the key (SV:763-767). A close the adapter keeps open stays registered (DEC-068, `test_DEC068_closeKeptOpenByTheAdapterStaysRegistered`).

6. **Reentrancy status**: namespaced slot of OpenZeppelin `ReentrancyGuard`; every state-changing entry except `setOperatingCashParameters` holds it.

Monotonic quantities: `cumulativeReceived`, `cumulativeSentHome`, `reportSequence`, `transitNonce`, `arrivalCount`, `arrivals[id]`, `operatingCash` (MVP), and `cumulativeIncome(token)` as a sum of adapter counters (Q60, SCL:121-127) under the assumption that each adapter's counter is monotonic.
