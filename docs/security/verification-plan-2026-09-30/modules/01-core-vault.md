**What this card changes in the plan (read first).**
1. Four exit-liveness or custody defects are confirmed by execution, not only by reading: CF-1 (an Instant claim panics forever when `payoutFeeBps + flowFeeBps > 10_000`), CF-2 (a paused or blacklisting income token blocks every full-burn claim), CF-3 (a Protocol Recipient that cannot receive USDC blocks every payout, deposit and income collection), CF-5 (`handleV3AcrossMessage` credits Idle without the DEC-080 backing check). They become P0 regression tests (W01) and founder decisions (section 10).
2. The existing invariant suite cannot see any of them: its handler has no transits, no reports, no failing dependency, no hostile token and swallows reverts (`test/unit/core/CoreVaultInvariant.t.sol:51,70,103`). The new handler (W04) is the backbone for Foundry, Medusa and Echidna.
3. Formal verification of this module is feasible only in a layered form: unbounded proofs for arithmetic, access control and single-transition deltas; the accounting sums (reserve, transit books, hub-bound ledger, income) close by a documented induction over proven per-function deltas plus a static writer-set check. Section 9 gives the harness (state injection at the pinned storage slots) that makes this tractable without touching `src/`.
4. Adversarial review (section 11, 2026-09-30): three more defects confirmed by execution in a scratch copy outside the clone: CF-12 (a successful but garbage-high price read pays an exiter 1,226.53 USDC for one share worth about 1 USDC, because PAYOUT mode bounds nothing and the variation band is 0), CF-13 (a spoke-to-hub arrival that no accepted report lists before the spoke prunes it stays in `unmatchedArrivals` for good), CF-14 (the timeout branch of `attestExpiry` frees the Spoke Cap of a transit that may have arrived, so a second full-cap send passes during a report outage). CF-6 is corrected in direction (a same-transaction pool move raises, never lowers, the oracle-valued hub principal, so the exploit is on exits). Seven properties added (INV-CORE-60 to 66), twelve restated, and the formal verification sections aligned with `03-FORMAL-VERIFICATION-PREPARATION.md` (tiers, directory layout, havoc models, class C route).

## 3. State and accounting

### 3.1 Units

- USDC amounts: base units, 6 decimals. Shares: 18 decimals, every mint and burn a multiple of 1e18 (`src/core/ShareToken.sol:47-58`, DEC-091).
- Share Price: USDC base units per whole share times 1e18, so 1e24 = 1.00 USDC (SM:8-12, SM:23); computed as `mulDiv(shareAssets, 1e36, totalShares)` and fixed at 1e24 when supply is 0 (SM:63-66).
- Token prices: `price1e18` = USDC base units per token base unit times 1e18 (CVL:305-316, `IPriceSource`).
- Income index: Q128 per share base unit (IA:22, IA:38).
- Spoke books mix units: `inFlightSent` in hub USDC, `inFlightToArrive` and `confirmedArrived` in spoke-token units (CVTy:60-66).

**Operating Cash**: at the start of `deposit`, `claimPayout`, `allocateToHubSpokeVault`, `sendToSpoke`, when `operatingCash < floor`, move `min(topUp, freeIdle)` from Idle (CVB:283-296); never the Payout Reserve (uses `freeIdle`, CVB:288).

**Valuation mode per entry** (CVL:47-52): MINT for `deposit` (reverts on a stale report CVL:205, stale price CVL:342, any failing dependency); PAYOUT for `requestPayout` and `claimPayout` (try on the hub report CVL:227 and on each price CVL:333, fallback to `lastHubValue` and `lastPrice`, never an age check); VIEW for the views and for the Spoke Cap check inside `sendToSpoke` (CVL:154, a reverting price source blocks sends, which is an entry and therefore acceptable).

## 9. Formal verification readiness

### 9.1 Strategy: prove steps, gate frames, close the induction on paper

A whole-contract "for all reachable states" proof of the Core Vault is not tractable as one query: every value-moving call runs a valuation that loops over report arrays, crosses a DELEGATECALL, calls six external contracts and uses 512-bit `mulDiv`. The plan therefore splits every state property `P` into four pieces, each with its own tool:

1. **L0, arithmetic lemmas** (W05): the rounding and fee facts every step relies on (INV-CORE-14 to 17, 20, 33, 50), proven over bounded widths (9.3) or unbounded where no `mulDiv` is involved.
2. **L1, inductive steps** (W06, W18): for each mutating function `f`, from an injected state satisfying `P` (plus the well-formedness lemmas it needs), one call of `f` with symbolic arguments and caller keeps `P`. External contracts are summarised by mocks whose answers are symbolic (9.5). The only callback that can run inside a guarded entry, `returnToIdle` during an unwind (CVB:174-178), is included as a nested step of `claimPayout` through the hub Spoke Vault mock.
3. **L2, frame conditions** (W07): a static gate proves that no function outside those proven in L1 writes the variables `P` reads (Slither writer sets, section 7).
4. **L3, closure**: `P` holds after the constructor (concrete unit test, INV-CORE-57) and is preserved by every function (L1 plus L2); by induction over transaction sequences `P` holds in every reachable state. Stateful fuzzing (W04, W10) is the empirical cross-check of the composition and of the assumptions.

The accounting sums (INV-CORE-04, 39, 44, 51, 52) are not expressible in L1 without ghost storage, which none of Halmos, hevm or Kontrol offers over Solidity mappings. They are proven as **delta lemmas**: "the aggregate changes by exactly the change of the one touched element, and one other symbolic element is untouched", which together with L2 implies the sum identity by induction.

**Alignment with `03-FORMAL-VERIFICATION-PREPARATION.md` (review, binding where the two differ).** L0 to L3 map onto 03's tiers: L2 is V0 (writer sets), a green L1 step is V3 (V3-bv on a loop-free class A or B check, V3-k in Kontrol), L3 closed by `check_closure.py` is V4, and every bounded result is V2 with its box printed in the label (03 section 1.1, rule 1.3-3). The core's targets are 03 section 1.4, row CV: B-CORE-LEDGER (01, 02, 03, 05) at V4 with 03 "modulo the 04 closure", 01 conditional(A-USDC) with its `handleV3AcrossMessage` step conditional(A-ACROSS-1); 12, 32, 33, 38 per writer, 40, 55 V4; 08, 29, 30 V3; 14 to 17 and 50 V3-k through the ShareMath lemmas; 06, 07, 47, 09, 10, 11, 21, 27, 48 per exit-matrix cell, 22, 23, 25, 26, 34 to 37, 41 to 43, 49, 53, 54 at V2; delta lemmas V3 plus literal sums V1 for 04, 39, 44, 51, 52; 18, 24, 28, 46, 59 V1; 19 fork; 13, 56, 58 V0; 31, 57 unit; 20, 45 `cover_`.
