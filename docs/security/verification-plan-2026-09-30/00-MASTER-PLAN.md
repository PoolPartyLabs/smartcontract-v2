## 1. Answer in one page

**What we will do.** Verify the frozen audit candidate from the test side only: no file under `src/` changes unless the founder rules on a defect (FV section 6; every edit changes the metadata and the bytecode, FV [F9]). Each property is written once (a registry row plus one pure predicate) and run by every engine that can take it, so the founder's 13 tools become thin consumers of one specification (FV section 3). Defensive posture everywhere: hostile manager inside the Mandate, hostile tokens, donors, griefers, relayers that skip or reorder, and every dependency failing alone or together; adapters trusted only at their pinned codehash (SV:188-195, CVL:657).

**Tools.** 12 of the 13 run on at least one file: Slither, Aderyn, Solhint, Wake (detectors only), Echidna, Foundry, Medusa, Halmos, hevm, Kontrol, Scribble (generated overlay on an instrumented copy, never on `src/`) and Mythril (bounded: 30 minutes per runtime in the `mythril/myth` image pinned by digest, only on the four runtimes that contain no MCOPY, ManagerFeeVault, ManagerRegistry, TransitEscrow and ChainlinkPriceSource, and on their Scribble-instrumented copies; it carries no registry property and is an exceptions-and-SWC second opinion expected to re-find the CF-R2 panic, section 2.1 row 5). Mythril is SKIP where the runtime contains MCOPY (its opcode table has none and its last release is 2024-03-27, T 5.9), which is every other runtime of `src/` except CoreVault, whose own 19,981 bytes have none but which runs CoreVaultLogic (3 MCOPY) by DELEGATECALL, so its results would be unsound across that call; Manticore is SKIP everywhere (archived since 2026-06-24, no PUSH0, MCOPY or TLOAD, T 5.10), while solc 0.8.28 for cancun emits all three here. Scribble on AB is a one-hour check inside the pilot, not a SKIP (section 2.1 row 6). Extras: `forge coverage`, `forge test --mutate`, `forge test --symbolic` (second engine only), `forge lint`, `forge test --brutalize` [S8].

**Order.** (1) Wave 0: pin the toolchain in isolated environments, fix the CI that has never passed (run 36713951710 failed at `forge fmt --check`, T section 1 item 1; card 07 AB-16), freeze baselines, build the registry, predicates, link route and slot maps (FV gate G0). (2) Phase 1: pin every candidate finding as a `test_<DEC>_FLAGGED_<slug>` test, close the 81 zero-hit branches (B 4.2), install the structural gates; output the founder decision pack. (3) Phase 2: stateful harnesses with hostile actors on every module, the offline factory-created fund (B gap G1), exit-liveness matrices, fork conformance on re-pinned archive blocks, formal calibration (gate G1). (4) Phase F (fix batch and re-baseline): the rulings of section 10.3, one fix batch on a new freeze tag (FB1, landed by the founder or a named owner), then its re-baseline (FB2): regenerated baselines, slot maps, link constants, coverage and mutation baselines, and a re-run of the phase 1 and 2 evidence on the new tag; skipped only if the founder keeps `e5c778a` (F-14). (5) Phases 3 and 4: formal verification bottom-up in FV order (pure libraries, small contracts, scalar cores, adapters, factory, library hosts, vaults), on the tag FB2 froze. (6) Phase 5: composition (hub pair, two chains, SYS-1 to SYS-7b, pairwise dependency sweep), mutation closure, release gate and audit evidence pack.

**What "done" means (release gate).** (a) Every one of the 454 property rows (66 core, 55 spoke, 52 share, 42 report, 51 V4, 51 Aave, 39 bridge, 44 factory, 54 math) and the 8 system rows has a status computed by CI from tool output, at or above its target tier, or FLAGGED with a founder question open, or ACCEPTED by a decision id (FV 1.1, 1.3). (b) Every zero-hit branch and line of `src/` is covered or listed with a reason (`--ir-minimum` artefact, unreachable, dead code on the INV-MATH-34 list). (c) No unexplained surviving mutant in any `src/` file. (d) Nightly fuzz campaigns clean for two consecutive weeks, each with non-zero effective-action counts. (e) Fork conformance green on re-pinned blocks for Uniswap V4, Aave V3, Across, Wormhole, Chainlink and USDC. (f) Release gate green: masked byte diff between the proven `verify` build and the deployment build (A-BUILD), library runtime hashes (A-LIB), factory wiring checks (card 08 W8, card 03 W10, card 05 V4-W19), the solc 0.8.28 known-bug review against the features used (transient storage, legacy codegen, the via-IR coverage build), and a chain-onboarding check for every chain a Mandate may list (opcode support, `CREATE2`, EIP-6780 and EIP-7702 behaviour, block gas limit against the 32M `createFund` plan). (g) The assumption monitor of package B53 has run against the release chains for two weeks with no open alert.

**Honest limits.** "Formal verification on all contracts" can only mean a tier per property with its bounds and assumptions (FV 1.1): every contract reaches at least V2 on access control, guards and frames; V3 and V4 are reachable for the custody core, the small contracts, the codecs and the adapter guards. No tier proves Uniswap, Aave, Across, Wormhole or Chainlink behaviour, gas, economics (spot manipulation, just-in-time income), keys or cross-chain deployment trust (FV 1.6; card 08 FF-10). Nonlinear rounding (class C) reaches V3 only if Kontrol passes the go or no-go of FV P-10; 11 of 17 bounded probes timed out or returned unknown (card 09 section 9.5). Every V3-k and V4-k label also needs Kontrol to run at all on the available runner (16 GB RAM and 16 GB swap recommended by its authors, T 5.12; peak memory, disk and time are measured in B02 Step 0): if it cannot, gate G1 falls back to INV-SHARE-01 at V3-bv (Halmos and hevm agreeing, all eight vacuity signals) and every k-label is deferred until a larger runner is budgeted (F-6). Several assumptions the vaults consume are known false today (A-PRICE, CF-R2; A-REG for a codeless registry, SF-1; A-SPK-1 in part, Aave F1 and F6 and CF-V4-1; A-ACROSS-2b, AB-11), so the affected rows stay `conditional` or FLAGGED until the founder rules. The plan finds and pins defects; it never fixes a business rule on its own.

**What the cards already found.** 33 candidate defects (informational items and duplicates excluded) were reproduced by scratch probes outside the clone (register seed in section 8.4), among them exit blocks and custody gaps: an Instant claim that panics for good when `payoutFeeBps + flowFeeBps > 10_000` (CF-1, CV:226), a paused income token that blocks every full-burn claim (CF-2, CVI:57), a blocked Protocol Recipient or fee vault that stops payouts, deposits, collections and report delivery (CF-3, SF-2; VRR:201 unwrapped), an unbacked Across callback that credits Idle and can block `returnToIdle` (CF-5, AB-12; CVT:110-122), a garbage-high price that pays 1,226.53 USDC for one share (CF-12, CVL:333-334), a single-asset non-USDC unwind step that reverts every automatic unwind (T14, SV:883), donated aTokens that revert an Aave close (F1, AA:444, AA:494), and an approve-hook token that desynchronises a V4 position key (CF-V4-1, V4A:366). None is an auditor's verdict.

**Size and calendar.** 181 card work items, 84 of them P0, bundled into 64 packages over 32 waves of two (the 60 packages of the cards plus the four of the fix batch and its re-baseline). Planning estimate of this plan (section 6.9): about 277 agent-days for the full plan (about 255 if the founder keeps `e5c778a` and phase F is skipped), about 152 days of elapsed lane time with two executors, so about 30 to 35 weeks; the defensive baseline (phases 0 to 2: every pin, every branch gap, every stateful harness, fork conformance, formal calibration) is about 139 agent-days and 15 to 17 weeks, and the fix batch with its re-baseline adds about 22 agent-days and 14 lane-days. The earlier figure of about 243 agent-days and 27 to 30 weeks left out phase F, the same-wave dependencies of phase 4 and the extra items of the completeness review (section 2.2). FV section 9 estimated 148 agent-days for the formal workstream alone; all figures are Not verified until gate G1 recalibrates them against the first measured checks.

**What the founder must decide before wave 0** (section 10.1): the meaning of "formally verified" (tier per property), the scope cut, write access and branch policy for executors, `spec/` and two test-only submodules in the contracts repository, a public repository or a paid 16 GB runner for Kontrol (with the trigger of F-6), archive RPC secrets for the fork tier, whether `ZeroSharePrice` is a legal revert, and who lands the fix batch of phase F (F-14).

### 4.3 Property coverage

### 6.1.1 Where acceptance runs, and how the shared machine is protected (2.2 row 30)

The coordinator machine has 8 CPUs and 8 GB of RAM and is shared with other sessions (B 0, which also records that another session switched its `forge` during the baseline). Echidna's Haskell memory is unbounded by configuration (T 5.5), Medusa starts 10 workers by default (T 5.7), Halmos has `solver-max-memory` 0 (T 8.8), `forge coverage` peaks at 1.0 GB (T 2), and Halmos verdicts depend on solver timing (T 5.8). Two lanes plus the coordinator's R5 re-runs starting such processes at once would make results depend on the machine's load. Rules:
1. **Light acceptance** (forge unit and `ci` profile tests, formatting, builds, static tools on one module, `spec-lint`, gates) runs on the executor's machine and on the coordinator's clean checkout.
2. **Heavy acceptance** runs as a CI dispatch on GitHub-hosted runners (4 vCPU, 16 GB, T 9), never on the coordinator machine: fuzz campaigns of 600 s or more (Echidna, Medusa, forge `deep`), every symbolic run (Halmos, hevm, forge `--symbolic`, Kontrol), `forge coverage`, mutation, Mythril, and the coordinator's own R5 re-run of any of those. The executor starts it with `gh workflow run <workflow> --ref verify/<pkg>` (2.2 row 23) and attaches the run URL and artefacts to the hand-off. The three runner scripts (`run-campaign.sh`, `run-matrix.sh`, `kontrol-ci.sh`, B04) dispatch by default for campaigns of 600 s or more and for every symbolic run, and accept `--ci` explicitly and `--local` to override under the lock of rule 3; the wave tables show the commands, with or without the flag, and both mean the dispatch for these cases.
3. **Local fallback** when a heavy command must run locally: one heavy process at a time machine-wide, held by an atomic lock directory (`tools/env/heavy-run.sh` wraps the command, takes `mkdir "$TMPDIR/pp-heavy.lock"`, waits or fails when it exists, and releases on exit); Echidna with `--workers 1`, Medusa with `workers` 2, Halmos under a container memory limit or `ulimit -v` of 6 GB with `solver-threads` 2 (Not verified: the memory behaviour of `solver-threads`, T 8.8), hevm with `--num-solvers 2`. A Halmos or hevm result obtained under load is never attached as evidence if any query ended in a timeout: it is re-run in CI.
4. Wave tables that name two heavy commands in one wave (2.3: Echidna 1,800 s beside Medusa 600 s; 2.5: two Medusa campaigns of 1,800 s) therefore dispatch them as CI jobs, where the runners are separate.

### 6.4 When a package fails or a tool finds a real bug

- **Package fails its acceptance.** The coordinator classifies the failure (FV 5.18): harness defect, tool artefact, model artefact, specification error, or real defect. Harness or tool: back to the same executor once with a precise note; a second failure moves the package to lane A or splits it. A proof that does not terminate follows the ladder S1 to S9 of FV 5.17 and its stop rule (one agent-day per property for V2 and V3-bv, two for V3-k); the attempt is recorded in the registry row's history so nobody retries a dead end.
- **A tool finds a real bug.** Stop the line on that module: no further package touches its footprint until triage ends; other modules continue. Replay the counterexample concretely in forge (FV 1.3 rule 5), then write the minimal reproducing test named after the decision it breaks, `test_<DEC>_FLAGGED_<slug>` (or `test_CEX_<property>_<yyyymmdd>` in `test/regression/` for a solver counterexample), add its `cover_` twin, set the registry row to `expected: flagged(<id>)`, the coordinator adds the finding to the register (section 8) and a question to `docs/OPEN-QUESTIONS.md` of the contracts repository (executors never edit either, 6.2 item 7) with options, the research reading and the blocked property ids, and tell the founder the same day for severity S1 or S2. Never change `src/`, never bend a predicate to match the code, never decide a business rule; the ruling flips the pin and the `cover_` in the fix PR (FV 1.3 rule 6).
- **Engines disagree** (FV 8.2 item V8): a failure until explained. **A fuzzer breaks a WF conjunct**: every status proven under that WF is revoked (FV 8.2 item V3) until the WF is strengthened and re-proven.

## 7. CI pipeline target

Runner facts (T 9, [S16]): the contracts repository is public, so `ubuntu-latest` is free with 4 vCPU, 16 GB RAM, a 6-hour job limit, 20 concurrent jobs and a 10 GB cache; a private repository gets 2 vCPU and 8 GB, which cannot run Kontrol (decision F-6). Even the public runner is at the edge for Kontrol: its authors recommend 16 GB RAM plus 16 GB swap (T 5.12) and the runner has 16 GB RAM and 14 GB of disk (T 9); peak memory, disk and image size are Not verified until B02 Step 0 measures them (2.2 row 22), and the G1 fallback and the F-6 trigger say what happens if they do not fit. A workflow can be dispatched only when it exists on the default branch (2.2 row 23), so B01 lands the skeletons of `kontrol.yml` and `measure.yml` on `main` and every later package dispatches them against its own branch. Rules for every workflow (T 9): actions pinned by commit SHA, `permissions: contents: read` by default, `persist-credentials: false`, tool binaries checked by sha256 or image digest, no secret on pull requests from forks. Budgets are `timeout-minutes` caps; expected durations are Not verified until B02 measures each tool once.

Per pull request the blocking jobs run in parallel, so the wall time is bounded by the slowest one (30 minutes); the compute per PR is at most about 3 runner-hours of caps, free on a public repository. Every non-blocking job uploads its artefacts (corpus, lcov, SARIF, JSON, `kontrol list` output) and opens or updates one issue per tool with the reproducer path (T 9.1).

## 8. Findings workflow

### 8.1 Severity scale (coordinator reading under the defensive posture; never an auditor's verdict)

| Level | Definition |
|---|---|
| S1 Critical | holder value lost or locked for good, or an exit blocked for good, reachable by an unprivileged actor while every dependency behaves as documented |
| S2 High | the same impact, but it needs a hostile manager inside a Mandate the factory accepts, one failing or hostile external dependency (issuer pause or blacklist, a garbage oracle answer, a compromised bridge), or it hits every fund of a factory; or a repeatable value extraction |
| S3 Medium | a temporary exit block, a bounded loss or mispricing, the liveness of a non-exit path, or a deployment misconfiguration that a release gate can catch |
| S4 Low | needs a dependency outside its published behaviour and loses nothing; planning limits; observability with an effect |
| S5 Info | documentation, events, test gaps |

### 8.2 Static-analysis noise

Until B02 commits the triage, Slither, Aderyn and Solhint run as ratchets against the counts in `spec/baseline/static/{slither,aderyn,solhint}.json` and are non-blocking (2.2 row 21); a finding above the baseline is triaged in the pull request that adds it. Triage happens once per finding class and is committed: Slither through `slither.db.json` (`--triage-mode`) with each hidden result justified in the pull request; Aderyn through `aderyn.toml` exclusions with a comment per detector (T 8.3); `forge lint` through `[lint] exclude_lints` with a reason per rule and the count gate of B16; Solhint by switching the rules that fire on the 13 assembly blocks and 3 low-level calls off in `.solhint.json`, one reason per rule in `spec/baseline/static/solhint-triage.md` (no `solhint-disable` in `src/`). Justification comments are never added to `src/` without the founder, because any edit there changes the audited bytes (FV [F9]); until then the reason lives in `spec/baseline/static/<tool>-triage.md`. Classes expected to be noise (T 5.1): `reentrancy-*` on paths guarded by `nonReentrant` (48 uses), `timestamp` (35 uses), `calls-loop` over Mandate arrays, `divide-before-multiply` in basis-point math, `incorrect-equality` on zero guards. A hit on `arbitrary-send-erc20`, `arbitrary-send-eth`, `controlled-delegatecall` or `suicidal` is never noise (cards 02, 06, 07, 08 section 7). A finding that survives triage enters the register like any other.

### 8.3 From finding to test to decision question

1. Replay: a concrete forge reproduction, never a solver trace alone (FV 1.3 rule 5).
2. Pin: `test_<DEC>_FLAGGED_<slug>` asserting today's behaviour with exact numbers, plus a `cover_` twin that must stay reached (FV 1.3 rule 6); the registry row becomes `expected: flagged(<id>)`.
3. Register: a row in `spec/findings/register.yaml` (id, card, evidence, severity, pin, cover, blocked property ids, decision question, status).
4. Question: an entry in `docs/OPEN-QUESTIONS.md` of the contracts repository with the options, the research reading of the card and the blocked ids; S1 and S2 are reported to the founder the same day.
5. Ruling: the founder decides; the fix pull request (outside this plan's packages) must fail the pin, flip the `cover_` to a `check_`, and pass `hevm equivalence` everywhere except on the intended paths.
6. Closure: the register row records the ruling's decision id and the pull request.
